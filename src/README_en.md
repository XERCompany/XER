# src

[English](README_en.md) | [Русский](README_ru.md)

This directory contains the core implementation of XER and its main runtime subsystems.

## Main areas

- `app/` — application shell: windows, NodeGraph app nodes, crash handler
- `async_io/` — asynchronous I/O, buffer pooling, scheduling, and hardware abstraction
- `audio/` — audio engine, DSP, effects, VST3/CLAP hosts, virtual audio cable
- `cache/` — caching utilities, persistence helpers, shared-memory channel
- `cef/` — CEF browser host (embedded Chromium views)
- `content/` — content-centric subsystems such as network, AI, and model integrations
- `flux/` — terminal and rendering runtime components
- `helper/` — utilities: strings, buffers, spans, raw pointers
- `lsui/` — `lsui.exe` — Lua scripts with UI windows
- `lunca/` — minimal packet/udp_socket protocol
- `media/` — media pipeline: demuxers, decoders, renderers, sinks, muxers, player
- `node_graph/` — graph model, executor, history, SQLite project store
- `sql/` — SQLite-backed persistence layer (ORM, query builder)
- `ui/` — WinAPI UI framework, 80+ widgets, CSS engine (`css/`), DevTools, XML UI
- `wrapper/` — bridges to external libraries: Skia, FFmpeg, CUDA, ANGLE, OpenCV
- `modules/` — JavaScript-facing modules exposed to the runtime
- `app_command.*` — command-line parsing and application entry helpers

## YA.*.dll packaging

Static project libraries are packaged into shared `YA.*.dll` modules via
`cmake/YaDll.cmake` (exports generated by `cmake/GenYaDef.cmake`).
Executables link the YA DLLs; third-party dependencies are embedded
statically inside them, so binaries run without a MinGW/MSYS2 runtime.

## High-level responsibilities

- runtime orchestration and dynamic compilation
- native execution and bridge integration with the JavaScript environment
- module registration and runtime plumbing
- low-level I/O, networking, buffering, and hardware interaction
- audio processing and DSP-related features
- AI and model-oriented backends with optional integrations

## Notes

The project is intentionally modular. Many capabilities live in dedicated subdirectories instead of a single monolithic runtime. This keeps the codebase easier to evolve while supporting optional features and platform-specific integrations.
